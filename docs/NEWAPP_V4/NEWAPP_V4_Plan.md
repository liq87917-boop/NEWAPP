01｜产品定位、用户与基本原则

1.1 产品定位

NEWAPP Work 面向义乌小商品市场及其他外贸采购场景，提供现场选品、商品拍照、报价记录、跨店铺历史比价

和客户资料导出；NEWAPP AI 负责提升效率；NEWAPP Supply 负责经授权的供应商协作；NEWAPP Connect 连

接 NEWERP、第三方 ERP 及外贸服务商。四条业务线可共享统一账号与基础服务，无需让用户安装四个 APP。

1.3 现场工作关键约束

-    业务员一名客户可连续走访几十家店铺；提交一家后保留当前客户上下文。

-    进入店铺页不进行全量店铺查询，必须由用户输入店铺号或其他条件触发搜索。

-    同一客户、店铺可能存在不同日期的多个询价批次；未提交草稿必须识别和恢复。

-    图片、价格、包装和备注要尽可能减少重复输入；AI 只做辅助，关键信息由用户确认。

-    闪退、断网、锁屏、关机、应用更新不能轻易损失已经成功持久化的数据。

02｜总体技术架构

           图：逻辑架构：移动客户端、本地数据、网关、业务服务、事件/Agent、存储与 ERP

2.1 架构选择

推荐“模块化单体业务后端 + 可独立扩展的 AI/Agent 任务执行器 + 事件/推送组件”。在规模未验证前不拆成大量

微服务。移动端通过统一业务 API 访问服务器，不直连服务器数据库；图片通过受控上传流程进入 OSS。

2.2 数据共享边界

-    NEWAPP 与 NEWERP 可以共享必要的业务主数据及 OSS，但统一确定客户、店铺、商品、报价等实体的维护

     责任。

-    避免 NEWAPP 与 NEWERP 各自复制出相互割裂的客户和商品主数据；对接优先通过业务接口/服务层。

-    平台公共店铺基础信息与组织私有价格、备注、交易明细分别存放或逻辑隔离。

-    数据库连接由服务器集中管理连接池、索引、批量/增量接口和缓存；移动端不得持有业务数据库凭据。

3.2 单组织唯一归属

一个 UserID 在任意时点最多属于一个有效 OrganizationID。个人注册默认归属个人组织，加入企业必须先处理个

人组织的转换或退出。企业员工离职时原企业客户、历史报价及单据不随个人账号迁出；个人所有数据转入企业

需要明示。

-     组织、部门、业务组、角色分别建模。一个用户可以属于同一组织内多个业务组，但不可同时归属两个企业组

      织。

-     组织唯一性由数据库约束/事务保证；邀请、审批、退出、交接、禁用全过程留历史记录。

-     客户列表仅显示当前业务员所在组授权的客户；个人未提交询价仅本人及明确授权人员可见；店铺公共查询不

      等于公开私有报价。

3.3 多台本人设备：可信设备登记 + 单主编辑权

                图：设备注册、主设备切换和旧设备离线数据恢复

初始建议最多登记 3 台可信设备；同一时刻只能一台拥有服务器端主编辑会话。备用设备可切换成为主设备，是否

允许已验证备用设备只读查看已同步资料作为单独策略。换机要求重新验证，并提示旧设备未同步数据风险。

 不可兼得的约束 无法同时保证“永久无限离线可写”和“旧设备在完全离线时即时失效”。建议采用可配置

 的短期离线授权、服务端单主写租约，以及失效设备的隔离导入与冲突合并。

04｜完整询价业务流程

                   图：客户→店铺→询价篮→本地保存→提交→下一店铺

4.1 标准流程步骤

1.   点击询价模块：进入有权限的客户列表；存在客户直接选择，无则快捷新建。

2.   选择客户：检查本人该客户的未提交询价批次，提示恢复对应店铺草稿或继续选择新店铺。

3.   进入店铺列表：默认空查询，不预加载全库店铺；输入店铺号、位置等条件后搜索。

4.   查到店铺则选择；未查到可带入已输入店铺号快捷新建。公共店铺档案支持查重与受控编辑。

5.   选择店铺：检查该客户+店铺+本人未提交批次，支持继续、查看、另建一个批次。

6.   进入询价篮：新增商品、复制相似商品、搜索历史同款、AI 识别录入；图片正式保留最多 3 张/商品。

7.   录完每个商品先本地保存，后台同步。用户可暂存离店，也可确认本店全部商品后点击提交。

8.   提交进行必填校验、货号检查、图片完整性检查、服务端幂等确认。服务器确认后锁定当前批次。

9.   成功后回到店铺搜索页，保留客户上下文，继续下一家店；全天结束再汇总客户选品与 Excel。

4.3 客户货号与跨店同款

区分不可变系统商品 ID、客户使用的货号、供应商原始货号。客户可配置前缀/起始序号和编码规则；编号一经使

用不回收；离线可预分配安全号段或使用唯一可离线编码。

同一客户相同产品可绑定同一客户产品档案，并挂接多家供应商报价；不同规格或明确要求分开管理时建立新产

品/新货号。历史搜索支持货号、名称、规格、图片和 AI 相似候选；价格比较必须核对币种、MOQ、计价单位、

报价时间与规格一致性。

4.4 提交、更正与活动汇总

“本地保存”“已同步”“已提交”必须有不同状态。用户可暂存离店；提交成功后该批次进入只读，错误需创

建有差异与历史的更正版本。单家店铺提交不等于整天客户询价结束；客户询价活动汇总多店铺、商品数量、异

常记录及 Excel 导出。

5.2 关键设计

-   本地加密数据库保存询价草稿与待办队列；大图本地受控文件存储，主列表只使用缩略图。

-   每个商品、图片、操作和提交申请分配稳定唯一 ID，服务端执行幂等去重；避免重复提交、重复扣费。

-   修改冲突采用版本检查；绝不静默覆盖其他设备或其他员工已修改的数据。

-   断网继续录入；闪退重启恢复客户、店铺、当前商品和询价篮；上传失败只进入重试队列，不删除原图。

-   退出登录、组织迁移、换机、强制升级及清理缓存时必须检查未同步业务数据。

-   当本地存储确实失败（空间不足、数据库损坏等），明确提示不能宣称“已保存成功”。

-   设备完全丢失或恢复出厂设置时，未同步数据可能无法找回，应在产品中明确揭示风险。

5.3 异常处理 SLA 与告警建议

同步失败首先在询价篮中展示状态；持续失败合并成一条可点击的业务消息；高风险数据迁移、换机和组织退出

须主动检查，必要时阻止继续直到用户完成安全处理。后台日志必须脱敏，不应上传客户完整报价和图片用于普

通故障诊断。

6.4 必须阻止的越权行为

-   Agent 不得直接从聊天内容推断并扩大当前用户权限；权限检查必须在业务 API 内再次执行。

-   第三方名片、图片 OCR 和外部消息不可作为系统指令；防止提示词注入导致数据泄露。

-   正式询价提交、对外报价、删除、组织权限变更、资金相关操作应采取审批和授权策略。

-   不得让普通业务 Agent 直接运行 SQL DDL、修改生产代码或部署版本。

-   AI 任务须可重试、取消、追踪费用；失败不应重复扣费；结果可由消息中心查看。

14.1 第一阶段明确不做的事

-     不为了商家营收出卖企业客户、私有报价和未经授权的采购意向。

-     不在初期部署大规模复杂微服务，也不引入无必要的高频手机后台轮询。

-     不把 AI Agent 直接赋予数据库超级权限、自动付款或生产代码部署权限。

-     不让核心录入和数据导出依赖 AI 付费。

-     不声称设备彻底丢失时也能恢复未同步的本地数据。

14.2 最终战略判断

    推荐路径 以永久免费、可靠的现场询价建立复用率；用 AI 订阅验证效率价值；以受授权的商家目录和企业

    Agent 拓展收入；当供需两端成熟，再发展找货撮合、外贸服务和全球采购网络。
